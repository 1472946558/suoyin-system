# 第 1 周执行包：骨架与模型冻结周

## 1. 第 1 周目标

本周目标不是追求完整可演示支付闭环，而是把项目推进到“可开写、可并行、可联调”的状态，冻结第一版产品骨架、权限口径和系统边界。

本周结束时应达成以下结果：

- 小程序端完成主路径页面骨架与页面清单冻结。
- 后台管理端完成老板主控台与店长受限运营台的首版页面骨架规划。
- 后端完成鉴权、组织、门店、账号、角色权限、系统配置的首版模型与 API 边界草案。
- 权限体系统一到“固定三级角色模板 + 能力码 + 数据范围”口径。
- 回收拍照、门店分级、支付主路径、模板化配置项的第一版规则冻结。
- 外部资源项单独挂起，不阻塞当前设计与开发拆分。

## 2. 按 Agent 的任务拆分

### `ai-tech-lead`

任务：

- 输出第 1 周执行包，统一本周目标、边界、禁止事项与验收口径。
- 冻结第一版权限方案、组织方案、回收拍照规则和模板化约束。
- 拉齐小程序、后台、后端三端的模块边界与开发顺序。
- 明确本周哪些事项先做、哪些事项因外部资源不足先挂起。

完成标准：

- 存在一份可直接指导本周执行的周包文档。
- 关键规则口径统一，团队内不再出现“角色是否自定义”“拍照是否强制 3 张”“后台只给谁用”等反复摇摆的表述。
- 本周主线明确为“骨架与模型冻结”，不是“抢做支付上线”。

### `ai-weapp`

任务：

- 输出原生微信小程序首版信息架构和页面落地顺序。
- 规划登录、首页、收银、黄金回收、订单、设置六大模块骨架。
- 标记哪些页面依赖后端真实接口，哪些页面本周可先用静态结构推进。
- 明确角色差异会影响哪些菜单、页面入口和按钮可见性。

完成标准：

- 小程序端页面清单、主导航结构、模块优先级明确。
- 登录、首页、收银、回收、订单、设置均有首版骨架定义。
- 页面权限差异点已列出，不再把权限写死在单页描述里。
- 可以支持后续直接进入页面搭建与接口联调，不需要再重开产品梳理会。

### `ai-frontend`

任务：

- 输出后台管理端首版骨架规划。
- 规划登录、首页、门店管理、账号管理、角色权限、商品管理、订单管理、回收单管理、支付配置、支付流水、系统配置、操作日志页面结构。
- 明确“老板主控台 + 店长受限运营台”的后台定位。
- 设计权限配置界面的首版信息结构，确保能力项与数据范围可表达。

完成标准：

- 后台首版页面地图完整，覆盖本期必要页面。
- 门店、账号、角色权限三块核心后台能力已优先排进第 1 周骨架范围。
- 支付配置和支付流水虽然本周不接真支付，也已有静态页与字段边界规划。
- 后台权限配置方案可以承接老板控权诉求，而不是纯概念描述。

### `ai-backend`

任务：

- 输出首版核心数据模型与 API 草案。
- 优先覆盖鉴权、组织、门店、用户、角色、能力码、数据范围、系统配置。
- 给出收银单、回收单、附件、支付流水的首版模型骨架。
- 明确多门店数据隔离、回调幂等、附件绑定等后续关键技术约束。

完成标准：

- 有一版可供前后端对齐的接口与模型草案。
- 权限控制不再依赖页面写死，而是落到能力码与数据范围口径。
- 回收单与图片附件存在明确绑定关系定义。
- 支付虽然未开真链路，但已预留统一下单、回调验签、流水落库、状态更新、幂等处理的位置。

### `ai-devops`

任务：

- 输出环境与交付依赖清单，供后续统一回填。
- 收敛测试环境、对象存储、域名、HTTPS、数据库、Redis、支付资料等准备项。
- 区分“本周阻塞项”和“本周可挂起项”。
- 为后续部署和联调预留清晰的资源清单口径。

完成标准：

- 外部资源项已被归档到统一清单，不再散落在聊天和文档中。
- 团队明确当前可先推进不依赖 `AppID`、商户号、域名、HTTPS 的工作。
- 后续联调前必须补齐的资源项清单完整可读。

### `ai-security`

任务：

- 输出本项目第一版安全门禁与提测前约束。
- 明确鉴权、权限审计、支付回归、图片访问控制、多门店隔离的最低要求。
- 将安全约束前置到执行包和后续验收标准中。

完成标准：

- 已形成明确门禁口径，而不是泛泛提醒。
- 团队知道哪些能力在缺少安全校验前不能提测、不能上线。
- 老板控权、支付、附件访问、多门店隔离四类高风险点已被单独标红。

## 3. 每项任务的完成标准汇总

为避免“写了文档但无法执行”，本周统一按以下口径判断是否完成：

- 能直接指导下一步开写，而不是停留在抽象建议。
- 能支撑多 Agent 并行推进，而不是依赖同一人反复口头解释。
- 能把前端、后端、权限、组织、拍照、支付预留口径对齐到同一版本。
- 能明确本周先做骨架与模型冻结，下周再进业务闭环联调。
- 能区分已冻结规则、待确认问题和外部依赖，不混写。

## 4. 本周禁止事项

- 禁止承诺 3 周完整交付，把团队节奏带偏到压缩排期。
- 禁止在权限体系上一步做到完全自由角色系统，本周按“固定三级角色模板 + 能力项 + 数据范围”推进。
- 禁止把权限判断写死在页面文案或前端按钮逻辑里，三端统一认能力码和数据范围。
- 禁止绕开回收拍照规则讨论，默认按“至少 2 张、最多 3 张，可切换必须 3 张”冻结。
- 禁止把支付做成只有按钮的演示占位，同时也禁止在本周强冲真实商户联调。
- 禁止因 `AppID`、商户号、域名、HTTPS、对象存储尚未到位而停掉本周骨架工作。
- 禁止忽略多门店隔离、附件访问控制、支付幂等这类后续高风险点。
- 禁止新增 PRD 未确认的大功能，如复杂营销、完整财务对账、审批流、深度硬件集成。

## 5. 本周验收口径

本周验收不看“功能是否全部做完”，重点看“执行底盘是否已经搭好”。验收通过需同时满足以下条件：

- 周目标、开发顺序、模块边界和关键规则已有统一文档口径。
- 小程序端与后台端都已有首版页面骨架范围，不再停留在模糊页面名。
- 后端已有首版模型与 API 草案，可支持前后端进入并行实现。
- 权限体系、门店分级、回收拍照、支付预留、模板化配置项五类规则已冻结第一版口径。
- 外部资源依赖已被单独收敛，团队清楚哪些事项挂起、哪些事项继续推进。
- 安全门禁已前置纳入执行约束，后续不会在老板控权、支付和图片访问上无门禁裸奔。

若以上任一项缺失，则视为“第 1 周执行包未完成”，只能算信息收集中，不能算正式进入稳定执行态。
