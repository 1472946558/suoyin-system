# 第一轮 Agent 执行简报：黄金回收收银小程序

## 当前挂帅小龙虾

- 负责人：`ai-tech-lead`
- 判断原因：这是一个新项目接入场景，当前最重要的不是马上写代码，而是先把需求、边界、权限模型、门店模型、附件方案定住。

## 第一轮结论

### 1. 可以立即确认的方向

- 第一阶段优先做微信小程序 MVP。
- 前端优先使用原生微信小程序，不引入 `Taro` / `uni-app`。
- 设计稿只作为视觉基线，不作为移动端逐像素蓝图。
- 权限必须按“能力集 + 数据范围”建模，不能只写死角色名。
- 多门店模型必须从第一版就带上 `org_id` 和 `store_id`。
- 回收图片必须走正式“回收单草稿 -> 上传 -> 绑定 -> 确认回收”链路。

### 2. 当前最值得先拍板的 5 件事

- 是否第一期只做小程序端，不同步做后台。
- 回收拍照规则是否默认“至少 2 张、最多 3 张”，还是直接“必须 3 张”。
- 权限第一期是固定三级角色，还是要允许自定义权限项。
- 支付第一期是否只做演示和记账，不接真实微信支付。
- 员工是否允许跨店，以及老板是否统一看全部门店。

## 各 Agent 反馈摘要

### `ai-pm`

- 已将项目收敛为两条核心主链路：收银结算、黄金回收。
- 指出最容易返工的 3 块：
  - 权限模型
  - 多门店组织结构
  - 回收单附件规则

### `ai-weapp`

- 建议改成移动端“关键流程独立页”结构，不要硬搬桌面后台布局。
- 第一周前端最合理交付：
  - 小程序基础工程
  - 角色化首页
  - 收银骨架
  - 回收录单 + 拍照上传骨架
  - 订单列表 / 详情静态页

### `ai-backend`

- 建议以 `org -> store -> user_store_role` 建立组织与门店关系。
- 建议核心表至少包含：
  - 用户、门店、角色权限、会员、商品
  - 收银订单、回收单、附件、系统配置、审计日志
- 建议图片链路：
  - 先建回收单草稿
  - 再拿上传凭证直传对象存储
  - 上传完成后写附件表
  - 确认回收时做张数强校验

### `ai-qa`

- 验收重点已经锁定：
  - 老板 / 店长 / 员工三类角色差异
  - 跨店数据隔离
  - 回收单图片强校验
  - 异常场景证据

### `ai-tech-lead`

- 技术底线：
  - 原生微信小程序 + TypeScript
  - 单体后端服务优先
  - 对象存储正式方案
  - 能力集权限
  - 门店严格归属
- 开发顺序：
  - 先冻结业务边界
  - 再定技术基线
  - 再做前后端骨架
  - 再联调收银与回收双链路

## 推荐执行节奏

### 第 1 周

- PM：补齐待确认问题并冻结 MVP。
- Tech Lead：补技术执行计划与接口边界。
- WeApp：完成移动端页面骨架和 `photo-uploader` 组件。
- Backend：完成核心表设计和最小接口草案。

### 第 2 周

- 前后端联调登录、门店切换、收银、回收单草稿、图片上传。
- 跑通老板 / 店长 / 员工三角色差异。

### 第 3 周

- QA 按主路径、跨店隔离、图片规则做回归。
- 同步准备微信小程序提审、域名、对象存储、隐私协议等外部条件。

## 当前阻塞项

- 还缺业务层面的最终拍板：
  - 后台是否同做
  - 支付是否真接
  - 图片规则最终形态
  - 权限是否固定角色
  - 员工是否跨店

这些项不拍板，开发可以先做骨架，但进入联调前一定要冻结。
