# 方案草案：黄金回收收银小程序

## 负责人判断

本项目由 `ai-tech-lead` 作为当前项目总技术负责人小龙虾挂帅，原因是它最适合处理“需求还在口头阶段、需要先建档和拆任务”的场景。当前范围已经升级为“小程序 + 后台 + 支付 + 模板化复用”。

执行链建议如下：

- `ai-pm`：整理 PRD、页面清单、验收标准、待确认问题。
- `ai-tech-lead`：输出技术执行计划、依赖顺序、风险边界。
- `ai-weapp`：负责原生微信小程序页面实现与前端主路径。
- `ai-frontend`：负责后台管理端页面与权限配置前端。
- `ai-backend`：负责账号体系、门店组织、订单 / 回收单 / 图片接口与数据模型。
- `ai-devops`：负责域名、部署、HTTPS、对象存储、支付回调环境。
- `ai-security`：负责支付、权限、敏感数据和账号边界审查。
- `ai-qa`：负责主路径验收和权限回归。

## 阶段方案

### 阶段 0：需求冻结

- 固化设计方向。
- 固化 MVP 范围。
- 冻结回收拍照规则、角色层级和门店层级。

### 阶段 1：设计与页面骨架

- 基于现有黄金收银设计稿，产出小程序页面信息架构。
- 先完成登录、首页、收银、回收、会员、设置等页面骨架。
- 同步完成后台首页、角色权限、账号管理、门店管理等后台骨架。

### 阶段 2：业务与数据闭环

- 接入账号、角色、门店、商品、会员、订单、回收单模型。
- 建立图片上传与回收单绑定。
- 完成权限裁剪与菜单显示差异。
- 接入支付下单、支付回调、支付流水与后台支付配置。

### 阶段 3：联调与验收

- 跑通老板、店长、员工三类角色主路径。
- 跑通 2-3 张图片上传校验。
- 跑通多门店归属与订单查看边界。
- 跑通后台权限控制和前后台联动。
- 跑通支付主路径与支付流水回显。

## 技术建议

- 前端先用原生微信小程序，避免在第一版引入 Taro / uni-app 的额外迁移复杂度。
- 后台管理端建议独立 Web 工程或独立后台模块，不要塞进小程序里硬做。
- 后端从一开始就按“门店 + 角色 + 订单附件 + 支付配置 + 支付流水”建模，避免后期权限体系推倒重来。
- 图片上传不要只做前端本地态，必须预留对象存储路径、附件表和回收单关联。
- 权限不要先写死到页面文案，至少做成角色能力表或接口返回能力集，并允许老板在后台控制。
- 支付不要只做按钮占位，至少要把商户配置、统一下单、支付结果回写、流水记录这条链路建出来。
- 模板化优先级提升，所有客户差异项尽量收敛为配置，不要散落在代码常量里。

## 风险提醒

- 设计稿偏后台收银系统，如果直接照搬到小程序，需要重新判断移动端信息密度和交互可行性。
- 权限和多门店如果第一版偷懒，后面会直接卡死扩店场景。
- 回收拍照一旦进入真实业务，通常还会追加水印、时间、位置、签字等留痕要求，建议数据结构预留。
- 后台与支付同步纳入后，项目已不再是轻量 MVP，必须接受周期和外部依赖同步上升。
- 如果模板化边界不提前设计好，做完一单后仍然很难复用给下一个客户。
