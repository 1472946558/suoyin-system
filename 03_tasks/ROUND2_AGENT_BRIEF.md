# 第二轮 Agent 执行简报：后台 + 支付 + 模板化版

## 已确认决策

- 老板自己在后台控制权限。
- 后台管理端要同步建设。
- 支付功能要做。
- 产品要按可复用模板建设，不是只服务当前单一客户。

## 当前项目判断

项目已经从“演示型小程序 MVP”升级为“微信小程序 + 后台管理端 + 真实支付 + 模板化交付”的首版产品项目。

当前挂帅小龙虾仍然是：

- `ai-tech-lead`

## 第二轮核心结论

### 1. 权限方案

- 第一版不建议一步做到完全自由角色系统。
- 推荐方案是：
  - 固定三级角色模板：老板、店长、员工
  - 老板可在后台勾选能力项
  - 数据范围控制：全部门店 / 本门店 / 本人
- 小程序、后台、接口都只认能力码和数据范围，不认页面写死逻辑。

### 2. 后台方案

- 后台第一版定位为“老板主控台 + 店长受限运营台”。
- 必要页面包括：
  - 登录页
  - 后台首页
  - 门店管理
  - 账号管理
  - 角色权限
  - 商品管理
  - 订单管理
  - 回收单管理
  - 支付配置
  - 支付流水
  - 系统配置
  - 操作日志

### 3. 支付方案

- 第一条真实闭环建议先做：
  - 微信支付
  - 现金记账
- 最小闭环：
  - 统一下单
  - 小程序拉起支付
  - 微信回调验签
  - 支付流水落库
  - 订单状态更新
  - 重复回调幂等

### 4. 模板化方案

这些能力必须做成配置，不要写死：

- 权限能力项
- 组织与门店结构
- 回收拍照规则
- 支付方式与支付配置
- 商品分类与编号规则
- 账号与角色模板
- 品牌信息
- 新客户初始化脚本

## 第二轮分工结论

### `ai-tech-lead`

- 建议按 4 周排期，不建议承诺 3 周完整交付。
- 开发主线改为：
  - 先配权限与组织
  - 再做业务闭环
  - 最后做支付和模板收口

### `ai-backend`

- 后端已经按“首版可交付产品骨架”思路设计。
- 需要优先原型化：
  - 权限引擎
  - 支付原型
  - 回收单 + 附件状态流
  - 多门店数据隔离
  - 模板开通流程

### `ai-frontend`

- 后台第一周最合理交付：
  - 基础工程
  - 登录 / 首页 / 门店 / 账号 / 角色权限骨架
  - 支付流水与支付配置静态页
  - 模板初始化基础入口

### `ai-devops`

- 当前最关键的外部资源：
  - 小程序 `AppID`
  - 微信支付商户号
  - API 域名与 HTTPS
  - 后台域名
  - 对象存储
  - 测试数据库与 Redis

### `ai-security`

- 上线前必须强制门禁：
  - 无后端鉴权不准提测
  - 无权限审计不准开老板控权
  - 无支付专项回归不准开支付
  - 无图片访问控制不准上线
  - 无多门店隔离验证不准上线

## 推荐 4 周排期

### 第 1 周：骨架与模型冻结

- 小程序：登录、首页、收银、回收、订单、设置骨架
- 后台：登录、首页、门店、账号、角色权限骨架
- 后端：鉴权、组织、门店、用户、角色、系统配置基础接口
- 环境：测试环境、对象存储、域名、HTTPS、支付资料清单

### 第 2 周：业务双链路闭环

- 收银主链路
- 黄金回收主链路
- 老板后台配置链路
- 订单 / 回收单 / 附件 / 商品 / 会员接口联调

### 第 3 周：支付与权限联动

- 微信支付主路径
- 支付流水
- 权限联调
- 多门店数据隔离回归

### 第 4 周：模板收口与提审

- 模板初始化
- 安全与异常回归
- 提审材料
- 可复制交付包

## 当前最可能卡住项目的事项

- 小程序主体和 `AppID` 不到位
- 微信支付商户号和证书不到位
- API / 后台域名和 HTTPS 不到位
- 老板后台权限口径没有最终冻结
- 后台是否只老板用还是店长也用，没有最后拍板
- 回收支付是做记录还是做真实出款，没有最终冻结

## 老板当前最该补齐的清单

- 小程序主体、`AppID`、管理员账号
- 支付商户号、证书、`APIv3 Key`
- 服务器、域名、HTTPS
- 对象存储账号
- 协作者微信号
- 隐私协议、用户协议、提审材料
- 利润 / 回收收益计算口径
